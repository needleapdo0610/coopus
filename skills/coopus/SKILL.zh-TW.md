# coopus

## 一件事

判斷現在在哪個階段，叫對的 coopus skill，並守住人和 AI 的分工。這個 skill 本身不產出 spec 或 code。

## 流程

1. 該不該做 → `coopus-should-we-build`
2. 需要哪些領域的專家判斷 → `coopus-expert-dimensions`
3. 把需求問清楚，寫成含驗收標準的 spec → `coopus-grill`
4. 實作，用最少、完整的改動 → `coopus-ponytail`
5. 回報問題或宣稱完成前，過證據關卡 → `coopus-evidence-gate`

## 怎麼選

| 情況 | 用哪個 |
|------|--------|
| 新點子、新產品、新功能，還沒確定要做 | `coopus-should-we-build` |
| 要設計架構、選技術，或進入自己不熟的領域 | `coopus-expert-dimensions` |
| 已決定要做，但需求還模糊 | `coopus-grill` |
| 有核准過的 spec，開始寫 code | `coopus-ponytail` |
| 要說「這裡有 bug / 漏洞」或「修好了 / 完成了」 | `coopus-evidence-gate` |
| 想新增一條規則、修改 do-not-copy 清單 | `coopus-evidence-gate`（新規則段落） |

- 從最前面還沒完成的階段開始。使用者直接要求寫 code，但沒有核准過的驗收標準時，先跑 `coopus-grill`，只補驗收標準那一段。
- 小改動（改字、改設定、一行修正）可以跳過 1 到 3，但第 5 步不能跳過。改字或改設定：實際執行會顯示它的程式，貼上修改前和修改後的輸出，再附既有測試的結果。修行為的 bug：附一個修改前失敗、修改後通過的測試。
- 只有在答案會改變做法時，才提議回到前一個階段。

## 人的角色

人只做三件事，其他都交給 AI：

1. 核准 spec 和驗收標準。驗收標準要在寫 code 之前核准。
2. 看證據，不看 code。交付一定要附上測試輸出、重現步驟、畫面或執行紀錄。
3. 核准新規則。AI 只能提議，人點頭才生效。

## 不要做

- 不要順著使用者的語氣附和。使用者要的是被挑戰。
- 不要用「請扮演專家」代替列出專家的思考維度。
- 使用者對驗收標準說 yes 之前，不要寫 code。「不要問我」「我趕時間」或再說一次「直接寫」，取消的是提問，不是核准：給一份預設驗收標準（最多五條），用一句話說明原因，最後寫「回 yes 我就開始」。小改動（見上）不受此限。
- 不要讓寫 code 的同一個 session 審查自己的 code。
- 不要自己新增或修改規則、清單、skill。
- 不要換語言：使用者用什麼語言寫，就用什麼語言回。

## 驗證做對了

每個階段結束時，回覆裡要看得到：
- 現在在哪個階段、下一步是哪個 skill。
- 這個階段需要人核准的東西（建議、spec、驗收標準、新規則），用一行列出。沒有要核准的就不寫這行。
- 小改動：只寫「小改動，已跳過 1–3 階段」和證據。

## 停下來問人

- 不確定是個人專案還是工作項目，而這會影響資料、權限或審核方式時。
- 要核准的東西還沒被核准，下一步卻需要它時。
- 任務會刪除、公開或分享 repo 外的東西時。
