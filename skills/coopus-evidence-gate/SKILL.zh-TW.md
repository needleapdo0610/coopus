# coopus-evidence-gate

## 一件事

沒有證據的主張不能進結論。這也包括新規則：沒有實際案例和人的核准，就不能變成規則。

## 回報問題（bug、漏洞、code review）

1. 先多列候選問題，不要只報「確定的」。AI 沒辦法自己確定，篩選交給證據。
2. 每個候選問題要附上其中一種證據，才能列為「已確認」：
   - 能觸發問題的輸入或 PoC，附執行結果。
   - 一個現在會失敗的測試。
3. 給不出證據的，標成「推測」，寫明缺什麼證據，不能放進結論或摘要。
4. 嚴重度要寫兩件事：攻擊者或觸發者從哪裡進來、需要什麼權限。寫不出來就降一級，並註明原因。

格式：

```
[已確認 | 推測] <一句話問題>
位置：<檔案:行號>
證據：<輸入 / PoC / 失敗的測試，附輸出>
嚴重度：<高/中/低>，入口：<...>，需要權限：<...>
```

## 宣稱修好或完成

1. 同一個重現測試，修改前失敗，修改後通過，兩次的輸出都要附上。
2. 既有測試全部通過，附上指令和輸出摘要。
3. 對照 spec 的驗收標準逐條打勾，每條附上對應的證據。
4. 交付時附上證據：測試輸出、重現步驟、畫面或執行紀錄。人看證據，不看 code。

## 寫和審分開

- 寫 code 和審查由不同 session 或不同模型負責。
- 審查方不能修改測試或驗收標準。發現測試有問題，回報給人。
- 寫 code 的一方可以新增測試。
- 只有在既有測試因為已核准的需求改變而失效時，寫 code 的一方才可以修改它。
- 寫 code 的一方絕不能為了通過而刪除測試、跳過測試，或放寬斷言或條件。
- 測試失敗而需求沒有改變時，修 code，不修測試。
- 不確定需求有沒有改變時，停下來問。
- 回覆裡列出每一個測試改動：`Test change: <test>, <added | updated>, <reason>`。

## 新規則（self-improvement）

1. 新規則一定要來自實際案例：哪一次、發生什麼、證據在哪。
2. 客觀檢查（測試、型別檢查、lint、重現步驟、實際數據）可以自己跑、自己修。
3. 判斷題（設計好不好、文案對不對）由另一個 AI 評分時，結果只能當參考，不能變成規則。
4. AI 只能提議，格式固定，由人核准後才生效：

```
Proposed rule: <規則一句話>
案例：<哪次、發生什麼>
證據：<連結、輸出、檔案>
怎麼檢查：<能自動檢查就寫指令；不能就寫「人工判斷」>
```

5. 能寫成自動檢查（lint、測試、腳本）的規則，優先寫成自動檢查，比寫在 prompt 裡可靠。

## 不要做

- 不要說「應該修好了」「看起來沒問題」。沒跑過就寫「未驗證」。
- 不要把推測寫進摘要、標題或 commit 訊息。
- 不要自己修改規則檔、skill 或 `docs/do-not-copy.md`。
- 不要因為一次偶發錯誤就提議永久規則，先確認能重現。

## 驗證做對了

- 每個「已確認」都有能重新執行的證據；每個「推測」都寫明缺什麼。
- 每個「完成」都有失敗到通過的紀錄，以及既有測試的結果。
- 每個測試改動都列出原因；沒有任何測試被刪除、跳過或放寬。
- 新規則都是 "Proposed rule" 格式，沒有任何規則在人核准前生效。

## 停下來問人

- 沒有辦法重現，也寫不出測試時。回報為推測，問人要不要繼續查。
- 不確定失敗的測試是不是因為已核准的需求改變而失效時，或修好需要修改驗收標準時。
- 問題可能涉及安全漏洞，而 PoC 會碰到正式環境或別人的資料時。不要執行，先問。
