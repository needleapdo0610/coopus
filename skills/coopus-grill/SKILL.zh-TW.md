# coopus-grill

## 一件事

在寫任何 code 之前，把模糊的需求問清楚，產出一份含驗收標準的 spec，並讓人核准。

## 怎麼做

1. 先確認「該不該做」有結論。沒有的話，先跑 `coopus-should-we-build`；小任務可以用三行代替：要解決的問題、誰會用、不做會怎樣。
2. 能自己查的事實就自己查，例如 repo 裡現有的寫法、套件版本、API 限制。不要拿來問人。
3. 把剩下的決策排成一棵樹，先問會影響最多後續決策的那幾題。
4. 每輪最多三題，格式固定：

```
1. <問題>
   建議：<你的建議答案>，因為 <一句話理由>
   如果選另一個：<做法會怎麼變>
```

   使用者回「yes」或「1 yes」就採用建議。
5. 只問答案會改變做法的問題。答案不影響做法的，直接寫成假設。
6. 問到沒有會改變做法的問題後，寫出 spec：

```
## 目標
## 不做的事
## 使用者與情境
## 做法摘要
## 驗收標準
- [ ] <可以觀察或可以自動檢查的條件，例如「輸入 X，回傳 Y」「測試 Z 通過」>
## 怎麼證明做對了
<要跑的測試、指令、重現步驟、要附的畫面或紀錄>
## 假設（請確認或推翻）
- A1 ...
## 待定
```

7. 請人核准 spec，特別是「驗收標準」和「假設」。核准後才交給 `coopus-ponytail`。

## 不要做

- 不要一次丟十幾題。
- 不要問可以從 repo、文件或網路查到的事。
- 不要寫「效能要好」「介面要直覺」這種沒辦法檢查的驗收標準。改寫成數字或具體行為。
- 不要在 spec 核准前寫 code，也不要寫「先做一版再說」。
- 驗收標準核准後，不要為了讓實作通過而修改它。要改，先回來問人。

## 驗證做對了

- 每題都有建議答案和「選另一個會怎樣」。
- spec 的每一條驗收標準，都能對應到「怎麼證明做對了」裡的一項檢查。
- 假設都列出來了，使用者可以逐條回「對」或「不對」。
- 回覆最後一行寫明：「驗收標準待核准」或「已核准，交給 coopus-ponytail」。

## 停下來問人

- 每一輪問題之後，都要等回答再繼續。
- 兩個合理做法差很多，而且沒有任何資訊能幫你選時。
- 需求和 `coopus-should-we-build` 的結論衝突時。
